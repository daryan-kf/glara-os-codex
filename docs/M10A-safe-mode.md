# Emergency containment — M10A

Owner-only `emergency.change` atomically changes any subset of automation, AI, email, calendar, onboarding, financial and inventory capabilities. Read versions from `emergency.state`, submit the expected versions plus a 10–500 character reason and an optional `INC-...` or `DRILL-...` incident ID. Stale or duplicate changes roll back the entire request. Every change records the authenticated actor, previous/new state, reason, incident and server time. Owner/Admin can inspect state; Admin cannot change it. Archived and unauthenticated users are denied by the existing server boundary.

`GLARA_RECOVERY_MODE=true` forces all capabilities frozen and cannot be overridden by an application Owner. It defaults absent/false outside a restore; set it before importing. This variable is a server-side containment override, not a replacement for M9 disabled-by-default enable flags or AI approval. Existing M9 Email and Calendar flags must remain false.

Financial and Inventory source writes are checked by the existing instrumented mutation wrapper, in the same transaction as the write; all relevant commercial/inventory table writes are intercepted. Reads and audit/history access remain available. Automation evaluation/worker dispatch, AI requests/provider start/proposal decisions/result completion, new internal provisioning, and Calendar prepare/dispatch are guarded. Email claim and final dispatch recheck the freeze without silently invalidating an approved queue item. A frozen queue is not permission to bypass consent, approval, idempotency or source-version checks when resumed.

In-flight limit: a committed HTTP request already handed to a provider cannot be recalled. A freeze after the last transactional dispatch fence may race that outbound request; record unknown state and reconcile, never blindly resend. An onboarding action already past its initial check may complete account creation; contain/revoke that account as part of the incident. Completed work is not rolled back. Privileged platform operators can bypass application controls using deployment credentials: protect and attribute those credentials separately (IR-03).

`securityAdmin.revokeUser` is an authenticated Owner action. It first archives the target and records an attributable pending operation, then invokes Convex Auth's supported `invalidateSessions`, removes recovery/verification codes, and records completion. On any intermediate error the target remains archived and the operation remains pending; investigate, then repeat containment to finish. It refuses self-revocation so the sole operator cannot casually destroy the recovery channel. This is not trusted Owner recovery. Framework session crypto remains unchanged; archived/missing/unassigned profiles cannot create a new session. Local tests cover fresh sign-in rejection, refresh/session/code removal and existing business-access denial. Hosted/browser proof is still required.

A universal public emergency endpoint was not added. These are backend operator APIs, without a new emergency UI. Runbook operators need a reviewed authenticated invocation or subsequent UI; never use an unauthenticated shortcut. Invitation lifecycle, supported privileged MFA, independent Owner recovery and attributable platform administration remain separate open controls.
