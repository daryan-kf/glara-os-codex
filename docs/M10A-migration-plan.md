# Production data migration preparation

Production is not created or imported during M10A. There is no approved real source dataset or user mapping. The isolated backup drill is **not** production migration acceptance. Do not import the development snapshot into production.

Inventory intended authoritative groups: approved company settings and reference catalogs; brokerages/lead sources/Realtors; properties/opportunities/quotes; projects/rooms/events/checklists; inventory products/assets/stock/reservations/movements; agreements/customers/invoices/payments/allocations/credits; legitimate communication consent/suppression/history; required audit provenance. Rebuild analytics projections from authoritative facts and reconcile. Business Owner must approve which groups actually migrate and establish source ownership.

Exclude fictional acceptance data, test identities/passwords, active sessions, refresh/recovery/invitation tokens, API keys, environment values, deployment credentials, provider OAuth material, active queue leases, automatic pending sends, old AI execution jobs, and temporary local artifacts. Historical communications may be imported only as immutable history with approved privacy scope; they must not be replayed. Provision real employees through the approved onboarding flow, not copied development credentials. Preserve retired/archived assets and financial corrections where policy requires; do not silently discard them.

Required real-source contract (the representative version-1 implementation below supports native commands only): a versioned source manifest with stable `(source_system, source_record_id, transform_version)` identities, content digests and a persisted source-to-target ID map; deterministic UTF-8 normalization; decimal strings converted to integer cents using existing money validation; dates retained as Vancouver business dates or UTC instants according to source precision. Validate duplicate contacts/asset codes, FK references, money totals/allocations, valid stages/statuses, prospect next action, user/role mapping and reservation overlap before write. Reject invalid rows into a restricted report with row identifiers/reason codes, not a raw payload dump.

Phases: approve/freeze source and snapshot; dry-run validation; reference/user mappings; CRM/sales; projects; inventory; commercial; approved history/audit; rebuild projections; reconciliation. Each phase records source/version/operator/target/start/end, accepted/rejected counts and checkpoint digest. Same identity+digest is a no-op; changed source digest is an explicit conflict; resume only after verifying prior checkpoints. Bounded batches are required. No unreviewed generic import endpoint is added here.

The fictional version-1 command package has been rehearsed on a real isolated Convex backend with dry-run rollback, checkpoint/resume, exact duplicate replay, changed-source conflict and invalid parent/money/date/role rejection. Reconcile counts, relationships, signed financial balances, Inventory identity/reservations and analytics independently before any customer access. M10B needs a separately authorized execution plan and named operator/verifier.

Rollback: before writes, abort safely; during a phase, retain the target frozen and repair by stable identity or discard a newly created isolated target. After financial/audit acceptance, use compensating changes with audit or a separately approved full restore, not blind deletion. Code rollback does not undo data. Unknown external effects require reconciliation before retries. No production import is authorized or claimed. Isolated native-command rollback, checkpoint recovery and compatible-code rollback have passed; arbitrary legacy-history conversion is outside the current concrete source format.

## Executable rehearsal and scope

`src/lib/security/migration.ts` validates a strict manifest (maximum 100 commands / 200,000 JSON characters), stable identities, SHA-256 package fingerprint and source commit provenance, explicit transform version and earlier-command references. `convex/migration.ts` is internal-only and requires development, an explicit migration opt-in and an exact loopback HTTP URL. `tests/support/m10-migration-package.ts` supplies 13 fictional commands across CRM, properties, opportunities, projects, catalog, quantity stock, customer billing, invoice issue/payment and settings. Existing staff identities and one won opportunity are fixture prerequisites; native mutations enforce their current roles, invariants and audit actors. The package does not import arbitrary historical agreements, provider events or AI conversations. Such sources need reviewed adapters before any real migration.

Run `python scripts/prepare-recovery-drill.py`, then `node --import tsx scripts/isolated-migration-drill.mjs` with the previously provisioned official local backend binary under the ignored acceptance directory. No hosted credentials are supplied. The tool starts a fresh loopback target, runs the six scenarios, compares authoritative snapshots and native financial balances, emits only sanitized counts/results, and stops the backend. Restricted artifacts must remain outside Git. Ten unit/security cases additionally reject hosted, production and opt-out targets. Restore/rollback uses the separate recovery drill documented in M10A-backup-recovery.md.

Completed packages retain their original checkpoint and completion timestamps on replay. An initial rehearsal caught and corrected timestamp mutation on a no-op replay; exact snapshot comparisons now cover the migration evidence itself. Invalid commands roll back their entire transaction; resume commits only validated remaining commands. Analytics generated by native commands remain subject to independent final reconciliation. This rehearsal is technical preparation, not an approved source mapping or business sign-off.
